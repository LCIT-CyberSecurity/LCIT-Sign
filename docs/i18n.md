# WebUI internationalisation

The LCIT Sign WebUI is available in French (`fr`), English (`en`) and German (`de`). English is the fallback language.

Only the **presentation layer** is translated. Nothing stored in the database, read from a directory or typed by a
person is ever translated or modified (see [What is never translated](#what-is-never-translated)).

## Choosing a language

Open the account menu (top right), then pick **Français**, **English** or **Deutsch** in the *Language* section. The interface
updates immediately: no sign-out, no page reload, no call to the server.

The choice is a browser preference only. It is stored in `localStorage` under the key `lcit-sign.ui.locale`, and nothing
else is written anywhere:

- no `locale` / `language` column, no table, no migration;
- nothing is saved in PostgreSQL or sent to the backend;
- nothing is synchronised from LDAP, Entra ID or Google Workspace.

Which language is shown is decided in this order:

1. the person's own choice, when one is stored (it always wins);
2. otherwise the browser's language (`navigator.language`): `fr-*` is French, `de-*` (`de-DE`, `de-AT`, `de-CH`,
   `de-LU`…) is German, `en-*` is English;
3. otherwise English (`es-ES`, `it-IT`, an unknown language…).

An unknown stored value is ignored and the browser's language decides. The page language (`<html lang>`) follows the
active locale; all three languages are left-to-right (`dir="ltr"`).

## Where the texts are

| File | Role |
| --- | --- |
| `frontend/src/i18n/index.ts` | i18next set-up, `SUPPORTED_LOCALES`, `setLocale()`, stored preference |
| `frontend/src/i18n/fr.json`, `en.json`, `de.json` | The catalogues (same keys in all three) |
| `frontend/src/i18n/format.ts` | Dates, sizes and sorting in the active locale (`Intl`) |
| `frontend/src/i18n/enums.ts` | Labels of stable API values (`PENDING`, `ACTIVE`…) |
| `frontend/src/i18n/errors.ts` | Wording of the server's fixed sentences (see below) |
| `frontend/src/i18n/connectors.ts` | Texts of directory and mail connectors (see below) |
| `frontend/src/i18n/catalog.test.ts` | Catalogue contract tests |

The stack is `i18next` + `react-i18next`, with JSON catalogues and semantic keys (`nav.tracking`, `documents.upload…`,
`campaign.status.ACTIVE`). Components call `useTranslation()`; code outside components uses the `i18n` instance.

## Adding or changing a text

1. Add the key to `fr.json` (the wording of the French UI is the reference), to `en.json` **and** to `de.json`. The key
   sets must be identical: `npm test` fails otherwise.
2. Use the key: `t("documents.title")`. Never build a sentence by concatenation; use variables instead:
   `t("users.lastSeen", { date })`.
3. Counts use i18next plurals. English and German have `key_one` / `key_other`. French keeps a single sentence, in the existing
   `document(s)` style, under the plain `key`; both are found with `t("key", { count })`.
4. Text with markup inside uses `<Trans i18nKey="…" components={{ strong: <strong /> }} />`. Do not name a tag after
   an HTML void element (`<track>`, `<link>`…): the parser treats it as self-closing.
5. Texts shown from a TypeScript function (not a component) use `i18n.t(...)`.

`catalog.test.ts` also checks that all three languages use the same `{{variables}}` and the same markup tags in every text.

## What is never translated

Everything that is data: document, campaign and group names and descriptions, people's names and e-mail addresses,
directory values (DNs, attributes), tenant names, client IDs, issuers, subjects, UUIDs, hashes, file names, comments,
the content of PDFs, audit events and logs, exports and the consent text held by the server (it is part of the proof).
The audit `action` and `result` values are shown exactly as stored.

API values are stable and never replaced. Only their label is translated: `PENDING` is displayed *À signer* in French
and *Pending* in English and *Ausstehend* in German, `ACTIVE` as *Active*, and so on. A value the interface does not know is displayed as the API
sent it.

## Messages that come from the server

The backend is untouched by this work. Some of its answers are fixed sentences (partly French, partly English) that the
interface shows to the person. `i18n/errors.ts` maps those known sentences (by exact pattern) to catalogue keys so they
follow the interface language:

- error messages of the API (`errorText()`),
- the reasons why something cannot be deleted (`blockerText()`),
- the one-line details of the diagnostics page (`diagnosticText()`).

Anything not in those tables (an error body from Microsoft or Google, a technical detail, a value a person typed) is
displayed exactly as received. Logs and audit records are never translated.

Directory and mail connectors describe their own settings (label, help, example, set-up steps). Their texts are in the
catalogue under `connectors.<dir|mail>.<source>…` in every language. The French catalogue entry is the server's own
sentence: the catalogue is used when the server sends exactly that text, and the server's words are shown otherwise
(another build, a new setting).

## Dates and numbers

Stored timestamps and numbers are never altered. Only their display uses `Intl` with the active locale
(`fr-FR`: `02/10/2026`; `en-GB`: `02/10/2026`; `de-DE`: `02.10.2026`; day and month always on two digits, so a date is never ambiguous).

## Out of scope

- **E-mail notifications** and **server-generated reports/certificates** are built by the backend. Translating them
  would need a per-recipient language, which means storing one; this work deliberately stores nothing, so they stay as
  they are.
- Backend logs, audit records and API field names.
